Architecture Audit — What's Wrong With Flux?

Lesson 2 · ~15 minutes

The skill: Architecture audit

Before you can fix a system, you need to know what's broken. An architecture audit is a systematic evaluation of a system's design. It's a core skill: the ability to look at unfamiliar code and quickly identify where the design works, where it doesn't, and what to fix first.

The audit methodology (you can apply this to any system):

  1. List the modules — what are the pieces?
  2. Map dependencies — what depends on what?
  3. Evaluate each boundary — is the interface clean? Is coupling low? Is cohesion high?
  4. Identify hot spots — where do the problems cluster?
  5. Rank by impact — what hurts most and is cheapest to fix?

Let's apply this to Flux.

Step 3: Evaluate boundaries

Problem #1: Duplicated manifest type — two sources of truth

src/shared/types.ts defines PluginManifest and FeedContrib. src-tauri/src/lib.rs re-defines the same structs (lines 15-38). They must stay manually in sync. This is a maintenance coupling problem: any change to the manifest schema requires touching two files in different languages.

Files: src/shared/types.ts ↔ src-tauri/src/lib.rs:15-38

Problem #2: Hardcoded cookie path — implicit coupling

Both yt-feed/main.ts:15 and yt-auth/main.ts:18 hardcode the same path: join(import.meta.dir, "..", "..", ".youtube-cookie"). This path depends on the directory nesting being exactly plugins/youtube/plugins/yt-feed/. Move the plugin — path breaks. This is fragile implicit coupling through a shared file system convention.

Files: plugins/youtube/plugins/yt-feed/main.ts:15, plugins/youtube/plugins/yt-auth/main.ts:18

Problem #3: Three layers of timeout — conflicting strategy

The Rust host enforces 15s (lib.rs:206). yt-feed enforces 8s internally (main.ts:59). feed-widget enforces 15s frontend-side (feed-widget.tsx:88). The tightest timeout (8s) wins for yt-feed, but for other plugins only the outer Rust timeout applies. This is inconsistent — different plugins experience different timeout behaviors, and the frontend timeout duplicates the host's job.

Files: lib.rs:206, yt-feed/main.ts:59, feed-widget.tsx:88

Problem #4: feed-widget's DOM kill switch

forceClearLoading() (feed-widget.tsx:161-169) directly manipulates the DOM to remove a loading indicator because React state didn't reliably update. This is a design smell — a React component that bypasses its own state management means the rendering model is not trusted.

File: feed-widget.tsx:161-169

Problem #5: Serial request processing in shared stdin

#shared/stdin.ts processes requests one at a time (serial queue in processNext(), line 26-36). The Rust host maps responses by ID and can handle out-of-order responses, but the plugin can't send a response until the current request finishes. If yt-feed's feed method takes 8 seconds, a concurrent resolve call blocks behind it. This is a performance coupling between methods that should be independent.

File: plugins/_shared/stdin.ts:26-36

Problem #6: player-modal is a stub with no backend

The modal shows/hides but has no actual video playback. The movi-player slot is created but never properly wired. The event chain (player-load → modal-show → ...) has a known mismatch: the card dispatches player-load but listeners expect modal-load.

Files: player-modal.tsx, AGENTS.md (known issue #1)

Problem #7: Error handling is all strings

Every error in the system is a plain string. Rust returns Result<Value, String>. Plugins send {"error": "message"}. The frontend patterns through with ?? operators. No error codes, no structured errors, no categories. You can't programmatically distinguish "not authenticated" from "network error" from "timeout."

Problem #8: core-serve is vestigial

Spawed as a subprocess but does nothing — Vite dev server handles serving. Consumes a process slot and adds startup latency.

Problem #9: Build script writes temp files into plugin directories

.vite.config.mjs, entry.tsx, style.css are created inside each plugin directory during build. If interrupted, these remain as garbage. Adding a plugin requires modifying the build script's config generation.

File: scripts/build-plugins.ts:154-183

Step 4: Hot spots

Problems cluster in two areas:

  1. The plugin protocol — duplicated types, inconsistent timeouts, serial processing, string errors. The interface between Rust host and plugins has the most design debt.
  2. The frontend state management — feed-widget's kill switch, event name mismatch, untrusted React rendering. The frontend architecture is fragile.

Exercise: Choose where to start

Look at the roadmap above. The first 5 problems are all about the plugin protocol — the interface between the Rust host and plugin subprocesses. This is the core architectural interface of Flux, and it has the most issues.

Primary source

This whole lesson is an application of the concepts from A Philosophy of Software Design (Ousterhout). Chapter 1 introduces the idea of strategic vs tactical programming — the audit shows that much of Flux was built tactically (one feature at a time) rather than strategically (with the system's long-term health in mind).

For the audit methodology itself, see MIT 6.033: Computer System Engineering — Lecture 1 covers modularity analysis.
