What Is System Design?

Lesson 1 · ~10 minutes

The problem

Software gets complicated fast. A 10,000-line program has too much going on for any one person to hold all of it in their head at once (humans can keep roughly 7 things in working memory). Add another zero and the problem squares: interactions between parts multiply faster than the parts themselves.

This is the complexity problem. System design is the art of fighting it.

The solution: modularity

Modularity means dividing a system into pieces — modules — each of which you can understand on its own, without knowing what's happening inside the others.

Imagine a kitchen. You don't need to know how the fridge works to use it. You open the door, food is cold. The fridge abstracts away its compressor, coolant, and thermostat. That abstraction is the point: you only need to understand one module at a time.

In software, modules can be classes, packages, services, processes — anything that groups related code behind a boundary.

The quality metric: coupling and cohesion

Not all modularity is good modularity. Two properties tell you whether your modules help or hurt:

Coupling is how much one module depends on the internals of another. Low coupling is good — you can change module A without touching module B. High coupling is bad — a change in one ripples through the rest.

Signs of high coupling:

  • Changing module A forces you to also change module B
  • To use module A, you need to understand module B's internals
  • Tests for A need to set up B

Cohesion is how tightly the things inside a module belong together. High cohesion is good — everything in a module serves one clear purpose. Low cohesion is bad — the module is a grab-bag of unrelated stuff.

Signs of low cohesion:

  • A module with "and" or "utils" in its name
  • A class that does I/O, formatting, and business logic
  • Half the module's exports are used by other modules, not internally

These two are the primary diagnostic tools in system design. When you look at a system, you ask: is this coupled? is this cohesive?

The mechanism: interfaces (contracts)

If modules are the pieces, interfaces are the joints. An interface is the agreement between two modules: what one exposes and the other consumes. A good interface is:

  • Stable — it doesn't change capriciously
  • Minimal — it exposes as little as possible
  • Abstract — it hides implementation details

A bad interface is a leaky abstraction: it forces the consumer to know about the implementation anyway. For example, if using a "database" module requires you to know whether it's SQLite or PostgreSQL under the hood, the abstraction leaks.

The mindset: tactical vs strategic

Tactical programming means focusing on shipping the current feature, letting design quality slide. It's fast now, but the system degrades over time — each tactical shortcut makes the next change harder.

Strategic programming means investing extra effort to improve the design as you go: extracting a module, stabilizing an interface, cleaning up a boundary. It's slower now, but keeps the system healthy.

Neither is wrong. The skill is knowing when to be tactical (prototypes, experiments) and when to be strategic (core interfaces, shared infrastructure).

Quiz

Practice retrieval before moving to the exercise. Answer each one, then click to check.

Q1: The main reason we modularize software is:

  1. To make it run faster
  2. To let one person understand the system one piece at a time
  3. To reduce the number of files
  4. To make it object-oriented
Show answer

B. The primary goal of modularity is managing complexity — letting you understand one module without understanding everything else.

Q2: Low coupling means:

  1. Modules share many dependencies
  2. Changing one module does not require changing others
  3. The system has few modules
  4. Modules are small
Show answer

B. Low coupling means independence — modules can change without rippling to their neighbors.

Q3: A "leaky abstraction" is an interface that:

  1. Has a bug
  2. Forces the user to understand the implementation it was meant to hide
  3. Is documented poorly
  4. Changes frequently
Show answer

B. The abstraction "leaks" when the hidden complexity still shows through. The user still has to think about what's underneath.

Exercise: Spot the design

Now apply the concepts. Open plugins/peertube/plugin.json and the corresponding plugins/peertube/main.ts in your editor.

Step 1 — Identify the module

What is the module's responsibility? Write it in one sentence.

Hint

Look at the methods in plugin.json — what can this plugin do? That's its interface.

Step 2 — Evaluate cohesion

Does everything in main.ts serve that single responsibility, or does it do unrelated things?

Step 3 — Evaluate coupling

What does this plugin depend on? Does it import or call anything outside its own directory? What would break if the JSON-RPC protocol format changed?

Step 4 — Check the abstraction

The plugin exposes methods via JSON-RPC. Do those method signatures reveal implementation details (e.g., auth tokens, URLs, internal IDs) or do they hide them?

You don't need to write anything down — just think through each step. If you get stuck, ask me.
