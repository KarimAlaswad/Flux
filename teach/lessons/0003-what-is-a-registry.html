What Is a Registry?

Lesson 3 · ~25 minutes

The problem you already hit

In our grilling session, I said "the Registry should be a separate piece" and you said: "I don't understand what a registry is and why it's needed."

This is the right question. Let's build the concept from scratch using what you already know about Flux.

The front desk analogy

Imagine a large office building. You're a delivery driver. You need to find "Acme Corp" to deliver a package. You have two choices:

  1. Without a front desk: You walk through every floor, open every door, and look for a sign that says "Acme Corp." If there are 100 offices, you check all 100. If Acme moves to a different floor, your route breaks.
  2. With a front desk: You go to the lobby. A person sits at a desk with a directory. You say "Where's Acme Corp?" They say "Room 204, third door on the left." You go directly there.

The front desk is a registry. It keeps a directory that maps "what you're looking for" to "where to find it." It's a single place you can ask, instead of searching everywhere.

Flux has the same problem. When the feed-widget needs YouTube videos, it currently calls __pluginRpc('yt-feed.feed', {}) — which is the equivalent of walking directly to "yt-feed's office." But what if:

  • yt-feed gets renamed to yt-home-feed?
  • Someone writes a better YouTube feed plugin in Python?
  • The user wants to swap yt-feed for invidious-feed?
  • yt-feed crashes and a backup needs to take over?

In all these cases, the feed-widget's hardcoded call breaks. The widget was written with the expectation that "the YouTube feed plugin is named yt-feed" — a piece of knowledge it should not need to have.

What a registry actually stores

A registry is just a table. In its simplest form:

| Capability (what you need) | Provider (who does it)    | Address (how to reach them) |
|----------------------------|---------------------------|-----------------------------|
| "feed.video"               | yt-feed                   | subprocess pid 1234         |
| "yt-auth"                  | yt-auth                   | subprocess pid 1235         |
| "video.player"             | movi-player               | subprocess pid 1242         |
| "core.manifest.scan"       | core-manifest             | subprocess pid 1230         |

Three columns, that's it. A plugin says "I can do X, reach me at Y." The registry writes it down. A consumer says "I need X." The registry reads the table and says "go to Y."

Where Flux already has one (but doesn't call it that)

Look at src-tauri/src/lib.rs, lines 215-230:

#[tauri::command]
async fn resolve_hook(
    state: tauri::State<'_, AppState>,
    hook: String,
) -> Result<Value, String> {
    let plugins = state.plugins.lock().await;
    let plugin = plugins
        .iter()
        .find(|p| p.hooks.contains(&hook))
        .ok_or_else(|| format!("No plugin provides hook: {}", hook))?;

    Ok(serde_json::json!({ "name": plugin.name, "methods": plugin.methods }))
}

This is a registry query! It searches the plugin list for one that has the right hook, and returns its name and methods. The state.plugins vector is the registry table. The problem is: it lives inside the Rust binary, mixed in with 300 lines of other concerns (spawning, routing, timeouts).

Key insight: Flux already has a registry — it's just embedded in the Rust host. The question from our grilling session is: does it need to be? What if the registry were a separate, swappable piece that any language could implement?

What the core looks like with vs without a separate registry

Without registry (current Flux)

The Rust binary does everything: discover plugins, spawn them, hold the list, route RPC, enforce timeouts. Every piece is a hardcoded structural dependency:

lib.rs {
  discover_plugins()  // filesystem scan
  spawn_plugin()      // subprocess lifecycle
  PluginHandle {      // hold name + methods + hooks
    name, methods, hooks, stdin, pending
  }
  resolve_hook()      // search PluginHandles
  call_hook()         // resolve + route
  plugin_request()    // route by name
}

With separate registry

The core does only one thing: start the Registry. Everything else goes through it:

Registry (separate piece) {
  table: Map<capability, provider>
  register(plugin)    // "I do X"
  resolve(hook)       // "Who does X?"
  health_check()      // "Are you alive?"
  list()              // "Show everything"
}

Core (minimal boot) {
  start Registry      // that's it
}

How this changes the philosophy of the system

Before: The system is a "host with guests"

The Rust binary is the landlord. It knows where every plugin lives, who they are, what they do. Plugins are tenants — they exist at the host's pleasure. The host decides everything. If you rewrite the host, all plugins break because they depended on the host's specific implementation.

After: The system is a "marketplace"

The Registry is the market square. Plugins are vendors who show up, rent a stall, and advertise "I sell vegetables" (capability). Consumers walk through the market and ask "where can I buy vegetables?" The Registry points them to the right vendor. The vendors don't know each other. The consumers don't need to know which vendor sells vegetables — they just need vegetables.

This is the decoupling that makes 100% modularity possible:

  • No plugin imports another plugin by name — they import a capability from the Registry
  • The core can be rewritten — as long as the new core can start the Registry and speak JSON-RPC, nothing changes
  • Plugins can be hot-swapped — unregister one, register another. The consumer never notices
  • Languages don't matter — the Registry is just another process that speaks JSON-RPC

Scaling: what a registry offers as the system grows

Right now Flux has ~11 plugins. But think about:

  • 50 plugins
  • 500 plugins
  • A community plugin store where anyone publishes
  • Plugins that depend on other plugins' capabilities

A registry makes all of these possible without changing the core:

What you wantWithout registryWith registry
New plugin type Modify the Rust host to understand it Plugin registers its new hook. Done.
Swap feed source Edit feed-widget's hardcoded plugin name New source registers same hook. Registry returns newest. Zero code changes.
Plugin crashes Host must detect and clean up Registry's health check notices. Marks it dead. Routes to backup.
Introspect the system Read lib.rs source code Query Registry: "list all capabilities" → returns everything live
Find what uses a capability Grep the codebase Query Registry: "who provides feed.video?" → instant answer
Dependency graph You can't know without reading every plugin Plugins declare what they need. Registry validates the graph at boot.

What the Registry is NOT

Some common confusions the research cleared up:

  • It's not a database. It doesn't store plugin data. It stores addresses and capabilities. The data still lives in the plugins themselves.
  • It's not a message bus. It doesn't route messages between plugins. It just says "plugin X is at address Y." The caller still sends the message directly.
  • It's not an orchestrator. It doesn't start or stop plugins. It just knows where they are.
  • It's not a configuration store. Though you could extend it to hold config (as Consul does with its key-value store), the core responsibility is discovery.

Source: Consul docs — Services Usage for the distinction between service registry and message bus.

Exercise: Trace Flux's current registry

Read the code, find where the registry lives

  1. Open src-tauri/src/lib.rs
  2. Find struct AppState (line 53) — this holds the plugins vector
  3. Find resolve_hook (line 216) — this is the registry query
  4. Find spawn_plugin (line 104) — this is the registry registration (it creates PluginHandles)
  5. Count: how many different responsibilities do these ~300 lines handle? (spawning, timeouts, manifest discovery, routing, hook resolution, error handling)

Now imagine extracting just the registry piece — the ability to register and resolve hooks — into a separate process. What would change? What would stay the same?

Hint: The Rust host currently does 6 things. A Registry process would do 1 thing (registration + discovery). The remaining 5 things stay in a smaller Rust core, or move into other specialized pieces.
