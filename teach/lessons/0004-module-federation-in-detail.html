Module Federation in Detail — The Runtime Module System

Lesson 4 · ~45 minutes · System Design

What Module Federation actually is

Module Federation (MF) is an architectural pattern and a runtime system for sharing JavaScript modules between independently-built applications. It was introduced in Webpack 5, and has since evolved into MF 2.0 — a multi-bundler, multi-framework platform managed by the @module-federation/enhanced package family.

At its core, MF solves one problem: how does application A import a module from application B at runtime, using the same framework instance, without rebuilding A?

Conceptual model: MF turns every application into both a potential library consumer and a potential library provider. The module boundary shifts from the file system (npm install) to the network (remote HTTP request). From the consumer's perspective, import('remote/Widget') looks like a dynamic import — but the module arrives from another running application, not from node_modules.

The two eras: Webpack 5 MF vs MF 2.0

There are two distinct versions of Module Federation, and it's important to know which one you're dealing with:

Feature Webpack 5 built-in MF MF 2.0 (@module-federation/enhanced)
Package Built into webpack 5 @module-federation/enhanced
Bundler support Webpack 5 only Webpack, Rspack, Vite, Rsbuild, Modern.js, Metro

This lesson covers MF 2.0. The concepts (host, remote, share scope) are the same in both versions, but MF 2.0 adds the tooling that makes it production-ready.

Core concepts

Producer (Remote)

An application that exposes modules for others to consume. Configured via the exposes field. A producer produces a remoteEntry.js (or mf-manifest.json) that describes what it offers.

Consumer (Host)

An application that consumes modules from producers. Configured via the remotes field. A host declares which remote applications it pulls modules from.

Bidirectional (Host+Remote)

An application can be both a host and a remote simultaneously — exposing its own modules while consuming modules from others. This is the most common pattern in micro-frontend architectures.

The runtime architecture

How a remote module gets loaded

When a host imports a remote module, this sequence happens:

┌─ HOST ─────────────────────────────────────────────────┐ │ │ │ import('remote/Widget') │ │ │ │ │ ▼ │ │ MF runtime intercepts the import │ │ │ │ │ ▼ │ │ 1. Fetch remoteEntry.js ◄─────── HTTP GET │ │ (or mf-manifest.json) │ │ │ │ │ ▼ │ │ 2. remoteEntry.js registers with Share Scope │ │ "I exist, I need react@^18, I expose ./Widget" │ │ │ │ │ ▼ │ │ 3. Share Scope negotiates shared deps: │ │ - Host has react@18.2.0 (singleton: true) │ │ - Remote needs react@^18 (singleton: true) │ │ - ✅ Match — reuse host's React │ │ │ │ │ ▼ │ │ 4. Remote's Widget chunk is fetched and executed │ │ (uses host's React instance) │ │ │ │ │ ▼ │ │ 5. Widget module is returned to the consumer │ │ │ └─────────────────────────────────────────────────────────┘

The critical piece is Step 3 — the Share Scope. Without it, each remote would bundle its own React, doubling memory and breaking hooks, context, and other singleton-dependent APIs.

The Share Scope

The Share Scope is a runtime registry of shared dependencies. It's a global data structure (attached to window.__FEDERATION__) that maps (packageName, shareKey, shareScope) to a module factory.

Every MF participant — host and remote alike — registers its shared dependencies into this scope when its remoteEntry.js loads. The scope then negotiates which version wins.

Pattern recognition: The Share Scope is a registry (lesson 0003). The capability is a package name + version range. The provider is a module instance in memory. The address is the module's exports object. This is the same pattern as DNS, service discovery, and Flux's resolve_hook — just at the JavaScript module loading level.

The remoteEntry.js manifest

Every producer generates a remoteEntry.js file. This is not the actual application code — it's a bootstrap manifest that:

  • Registers the producer in the Share Scope
  • Lists which modules are exposed and where their chunks live
  • Declares which shared dependencies the producer needs
  • Provides factory functions for the exposed modules

MF 2.0 also supports mf-manifest.json — a declarative JSON version of the same information. When configured with manifest: true, the producer emits both the JS entry and the JSON manifest. Consumers can reference the manifest URL instead of remoteEntry.js, which enables:

  • Dynamic type hinting
  • Resource preloading
  • Chrome DevTool debugging

Configuration deep dive

exposes

The exposes field declares which modules a producer makes available to consumers.

// module-federation.config.ts
export default createModuleFederationConfig({
  name: 'my-components',
  exposes: {
    './Button': './src/components/Button.tsx',
    './Card': './src/components/Card.tsx',
    './Widget': './src/widgets/Widget.tsx',
  },
});

Key rules:

  • Expose keys must start with ./ — this is not a convention, it's a spec requirement. "./Button" is valid; "Button" is not.
  • The value is a path relative to the project root (or the MF config location).
  • Exposed modules get extracted into separate chunks during the build.
  • Consumers import them by key: import('my-components/Button').

remotes

The remotes field declares which producers a host consumes from.

// Reference by remoteEntry.js:
remotes: {
  'remote': 'remote@http://localhost:3001/remoteEntry.js',
},

// Reference by mf-manifest.json (preferred for MF 2.0):
remotes: {
  'remote': 'remote@http://localhost:3001/mf-manifest.json',
},

The format is 'alias@url' where:

  • alias — the name used in imports (import('remote/Button'))
  • url — the entry point (either remoteEntry.js or mf-manifest.json)

Using the manifest URL (instead of remoteEntry.js) enables all MF 2.0 features: type downloading, resource preloading, and DevTool integration.

shared

The shared field is the heart of MF's dependency management. It declares which packages should be shared between host and remote, and how version conflicts should be handled.

Basic form: array of package names

shared: ['react', 'react-dom'],

This tells MF: "I use react and react-dom, and I'm willing to share them with other participants." MF will use the version from package.json as the requiredVersion.

Advanced form: object with per-package config

shared: {
  react: {
    singleton: true,
    requiredVersion: '^18.2.0',
    eager: false,
    shareScope: 'default',
  },
  'react-dom': {
    singleton: true,
    requiredVersion: '^18.2.0',
  },
},

Each field controls a different aspect of the sharing behavior:

FieldTypeDefaultWhat it controls
singleton boolean false Whether only one instance of this package may exist in the entire share scope. Set to true for React, Vue, Angular — libraries that use global state, context, or have side effects when multiple instances exist.
requiredVersion string Version from package.json The semver range this participant requires. If the resolved shared version falls outside this range, a console warning is emitted (or an error in strict mode).
eager boolean false Whether to include this dependency in the initial bundle instead of lazy-loading it. Use with caution — it increases bundle size but avoids async loading for entry-point dependencies.
shareScope string "default" Which named share scope this package participates in. Multiple scopes allow isolating different dependency pools (e.g., running two React ecosystems side by side: one in "default", another in "legacy").
shareKey string The property key The lookup key used in the Share Scope at runtime. Both producer and consumer must use the same shareKey for negotiation to succeed.
import string | false undefined Controls the actual import path. Set to false to declare a dependency without bundling it — rely entirely on a consumer providing it.
Common mistake: Forgetting the trailing slash on subpath imports. 'react-dom' only intercepts import 'react-dom'. Code like import { createRoot } from 'react-dom/client' will not be shared — it loads a second copy of React DOM, breaking the singleton contract. Fix: use 'react-dom/': { request: 'react-dom/' } in the shared config. See the shared config docs for details.

shareStrategy: version-first vs loaded-first

The shareStrategy controls how the Share Scope prioritizes which version of a shared dependency to use when multiple participants offer different versions:

StrategyBehaviorWhen to use
version-first (default) Prioritizes the highest satisfying version. All remotes are loaded during initialization so their shared deps are registered immediately. If a remote is offline, initialization may fail. Strict version requirements, controlled deployment environment, all remotes are expected to be available.
loaded-first Prioritizes reusing already-loaded dependencies. Remotes are loaded on-demand — only when a module is actually requested. Offline remotes don't block initialization. Performance-sensitive apps, unreliable network, partial availability tolerance.

The difference matters most when a remote is unreachable:

  • version-first: App initialization may hang or fail because the remote's remoteEntry.js can't be fetched during the init phase.
  • loaded-first: The host starts fine. Only the specific import('remote/Widget') call fails, which can be caught with an error boundary.

Version-first requires error handling for the errorLoadRemote hook with lifecycle: 'beforeLoadShare' — see the shareStrategy docs for the plugin pattern.

The Share Scope negotiation algorithm (in detail)

When a host loads a remote, the Share Scope goes through this decision tree for each shared package:

For each shared package P: 1. Is P already registered in the Share Scope? │ ├── NO → Register P from the current participant. │ (First registration always wins for "first version seen") │ └── YES → Is singleton: true on either participant? │ ├── NO → Load a separate copy for each participant. │ (Multiple instances coexist — works for utility libs) │ └── YES → Compare versions: │ ├── singletons match or one is │ compatible with the other's │ requiredVersion range? │ │ │ ├── YES → Use the higher satisfying version. │ │ Warn if lower-version participant │ │ exists but is usable. │ │ │ └── NO → Incompatible singletons: │ Error or fallback depending on config. │ (Two apps need react@^17 and react@^19 │ — no single version satisfies both.) │ └── shareStrategy? ├── version-first → Use highest available version. └── loaded-first → Use the already-loaded version.
Key insight: The negotiation is not a conflict-resolution protocol — it's a best-effort match. If versions are compatible, it reuses the loaded instance. If they're incompatible and singleton: true, it errors. If singleton is false, each side loads its own copy and they coexist silently. You control how strict or lenient the sharing is via these config knobs.

Type safety across module boundaries

One of MF 2.0's biggest improvements over Webpack 5 MF is automatic type generation and consumption. Just as npm packages ship .d.ts files, MF remotes can ship type definitions for their exposed modules.

How it works

RoleWhat happensConfiguration
Producer During build, MF runs TypeScript on the exposed modules and packages the type declarations into @mf-types.zip (or a custom name). Also generates @mf-types.d.ts for runtime API types. dts: { generateTypes: true } (enabled by default)
Consumer During build, MF automatically fetches the remote's @mf-types.zip, extracts it to @mf-types/<remote-name>/, and TypeScript resolves imports via paths. dts: { consumeTypes: true } (enabled by default)

Consumer tsconfig setup

// tsconfig.json
{
  "compilerOptions": {
    "paths": {
      "*": ["./@mf-types/*"]
    }
  }
}

With this, import('remote/Button') is type-checked against the actual remote types, not any. If the remote updates its Button props, the consumer's build catches the mismatch.

Advanced DTS options

OptionWhat it does
extractThirdParty: trueInclude types of third-party deps used by exposed modules (e.g., antd types). Needed when the consumer doesn't have antd installed.
extractRemoteTypes: trueInclude types from remotes that the producer itself consumes (nested type re-export).
generateAPITypes: trueGenerate types for the runtime loadRemote API — enables type-safe loadRemote('remote/Button') calls.
compilerInstance: 'tsgo'Use the faster TypeScript GO compiler for type generation (significantly faster than tsc).
compileInChildProcess: trueRun type generation in a child process (reduces memory pressure).

Cross-framework with Bridge

The Bridge is MF's solution for application-level, cross-framework module sharing. While basic MF shares components within the same framework (React ↔ React), Bridge enables sharing entire applications across frameworks (React ↔ Vue).

The Bridge contract

Bridge uses a simple render/destroy lifecycle contract that's framework-agnostic:

// Any framework exports this:
export default function createProvider() {
  return {
    render(info: { dom: HTMLElement; basename?: string }) {
      // Mount the app to the DOM node
    },
    destroy(info: { dom: HTMLElement }) {
      // Unmount and clean up
    },
  };
}

The consumer loads this provider and calls render on a DOM node it controls. Because the contract is just render and destroy on a HTMLElement, the actual framework internally is irrelevant to the host.

React Bridge APIs

// Producer side — export a React app
import { createBridgeComponent } from '@module-federation/bridge-react';

const provider = createBridgeComponent({
  rootComponent: App,
  renderOptions: { basename: '/remote-app' },
});

export default provider;

// Consumer side — load a remote React app
import { createRemoteAppComponent } from '@module-federation/bridge-react';

const RemoteApp = createRemoteAppComponent({
  loader: () => import('remote/export-app'),
  fallback: <div>Loading...</div>,
});

function Host() {
  return (
    <div>
      <h1>Host App</h1>
      <RemoteApp />
    </div>
  );
}

Component-level lazy loading

For finer-grained control, Bridge offers createLazyComponent — a per-component lazy loading API that builds in React.lazy, Suspense, error boundaries, and data prefetching:

const LazyButton = createLazyComponent({
  loader: () => import('remote/Button'),
  loading: <ButtonSkeleton />,
  fallback: ({ error }) => <ErrorFallback error={error} />,
});

Runtime diagnostics

Error codes

MF 2.0 emits structured runtime error codes prefixed with RUNTIME-. The most common:

CodeMeaningTypical cause
RUNTIME-001Remote entry load failureURL is wrong, CORS error, network down
RUNTIME-008Script execution errorRemote entry downloaded but threw during eval (syntax error, missing global)
RUNTIME-006Async entry not configuredMissing experiments.asyncStartup: true in bundler config
RUNTIME-007Shared dependency mismatchTwo participants require incompatible singleton versions

When you see one of these in the browser console, the diagnostic flow is:

  1. Is the remote entry URL reachable? (Check Network tab) → If not: RUNTIME-001 (network error)
  2. Is the URL reachable but the script throws? → RUNTIME-008 (execution error)
  3. Is the share scope complaining about version conflicts? → RUNTIME-007

Debug mode

Enable debug mode via browser console:

localStorage.setItem('FEDERATION_DEBUG', 'true');
// Then reload the page

This exposes the __FEDERATION__ global, which contains the full runtime state: all registered instances, their remotes, shared dependencies, and the current share scope contents. You can inspect it directly:

// In browser console:
console.log(window.__FEDERATION__);
// View: instances, remotes, shared scope, version negotiation results

Observability plugin

MF 2.5.0+ ships an @module-federation/observability-plugin that collects full loading traces — from manifest fetch through share scope negotiation to module evaluation. It outputs a structured JSON report with phases, timing, and failure points. When error codes alone aren't enough, this is the next step.

System design principle: Runtime error codes are the first signal — they tell you what broke. Observability reports are the second signal — they tell you where in the pipeline it broke. The combination lets you distinguish between network failures (fix the URL), build failures (fix the producer), and config conflicts (fix the shared config).

Putting it together: a complete configuration

Here's a complete MF 2.0 setup with two applications:

Producer (remote/)

// module-federation.config.ts
import { createModuleFederationConfig } from '@module-federation/rsbuild-plugin';

export default createModuleFederationConfig({
  name: 'my-components',
  filename: 'remoteEntry.js',
  exposes: {
    './Button': './src/components/Button.tsx',
    './Card': './src/components/Card.tsx',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^18.2.0' },
    'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
  },
});

Consumer (host/)

// module-federation.config.ts
import { createModuleFederationConfig } from '@module-federation/rsbuild-plugin';

export default createModuleFederationConfig({
  name: 'my-host',
  remotes: {
    'my-components': 'my-components@http://localhost:3001/mf-manifest.json',
  },
  shared: {
    react: { singleton: true, requiredVersion: '^18.2.0' },
    'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
  },
});

// src/App.tsx
const RemoteButton = React.lazy(() => import('my-components/Button'));

function App() {
  return (
    <Suspense fallback={<div>Loading...</div>}>
      <RemoteButton label="Click me" />
    </Suspense>
  );
}

Tying to Flux: system design perspective

The fundamental question: Where does MF fit in a system's dependency management strategy? And where shouldn't it?

Flux currently uses IIFE bundles with duplicated dependencies — each plugin bundles its own React. This is the maximally simple approach: zero runtime coordination, zero shared state, zero version negotiation. Each plugin is a completely independent artifact.

MF would let Flux share a single React instance across all plugins, reducing bundle size from ~600KB to ~130KB. But it would introduce:

  • A bundler requirement — all plugins must use a supported bundler (Webpack/Rspack/Vite with MF plugin), unless they use the pure runtime API
  • A runtime dependency — the MF runtime (~15KB) must load before any plugin
  • Version coupling — if a plugin needs React 19 but the host provides React 18, there's a conflict
  • Startup coordination — with version-first strategy, all remotes must be reachable during init

Compare with the alternative approaches:

DimensionIIFE (Flux now)MF 2.0ESM + import maps
Bundle size~160KB per plugin~130KB shared + ~2KB per plugin~130KB shared + ~2KB per plugin
Plugin independenceFull — runs on any hostPartial — needs compatible shared scopePartial — needs host to provide import map
Bundler requirementAny IIFE-capableWebpack/Rspack/Vite with MF pluginAny ESM-capable
Version conflictsNone (duplicated)Singleton conflicts can break thingsManaged via import map scopes
Runtime depsNone~15KB MF runtimeNone (browser native)
Type sharingNoneBuilt-in DTS generationManual
Cross-frameworkVia Bridge patternVia MF BridgeVia import map + any framework

For Flux specifically, the IIFE approach makes sense because each plugin is inherently isolated — they run as separate subprocesses, communicating over JSON-RPC. There's no runtime sharing between plugins to begin with. The duplicated React is in the frontend widgets (the Web Components that render on the host page), not in the backend subprocesses.

If Flux ever wants to share a single React instance across its frontend widgets, either MF or ESM+import-maps would work. The choice depends on whether you want the additional tooling (type generation, runtime diagnostics, Bridge) that MF provides, or the simplicity of a browser-native approach.

The system design skill: The right answer depends on your constraints. Flux optimizes for independence at any cost — each plugin must work on any host, forever, without coordination. That makes IIFE the right choice. A different system with different constraints (e.g., a large micro-frontend product where all teams use React) would optimize for sharing at any cost — and MF would be the right choice. The skill is knowing which trade-off to make.

Exercises

1. Trace the negotiation

Three applications participate in MF:

  • Host A: shared: { react: { singleton: true, requiredVersion: '^18.0.0' } } — has React 18.2.0
  • Remote B: shared: { react: { singleton: true, requiredVersion: '^17.0.0' } } — has React 17.0.2
  • Remote C: shared: { react: { singleton: true, requiredVersion: '^19.0.0' } } — has React 19.0.0

Trace what happens when each remote loads into Host A. Which React version does each remote end up using? Does any scenario produce a warning or error?

2. Config audit on Flux

Flux doesn't use MF, but let's think about what would need to change. Open scripts/build-plugins.ts and find the Vite config generation. Identify:

  • Where would you add the MF plugin config?
  • What would you put in exposes (what modules does each plugin expose)?
  • What would you put in shared? (Hint: React is already bundled. Would you switch to external + shared, or keep it bundled?)
  • What shareStrategy would make sense for Flux — version-first or loaded-first? Why?

3. The shareKey puzzle

A consumer configures:

shared: {
  'my-react': {
    import: 'react',
    shareKey: 'react',
    singleton: true,
  },
}

The remote configures:

shared: {
  react: { singleton: true },
}

Will these two negotiate successfully? Why or why not? (Hint: what's the remote's default shareKey?) What happens if the consumer omits shareKey: 'react'?

4. The version-first trap

Your team sets shareStrategy: 'version-first' on a production app. A remote's deployment goes down temporarily. What happens during app initialization? Is there a way to make it resilient without switching to loaded-first? (Hint: look at the errorLoadRemote hook.)

Follow-up questions

Some things to ask yourself — or ask me — to go deeper:

  • How does MF's Share Scope compare to Flux's resolve_hook registry? Both map a capability to a provider — but one maps package names to module instances, and the other maps hook names to plugin processes. What does that difference imply about their reliability and failure modes?
  • If Flux switched its frontend widgets from IIFE to ESM+import-maps (the recommendation from the research), what MF features would you lose? What would you gain?
  • The Bridge pattern's render/destroy contract is very similar to Flux's plugin lifecycle (start/stop via the subprocess). Is there a generalizable pattern here — "all cross-boundary modules should expose a lifecycle, not just exports"?
  • MF 2.0's DTS generation is essentially cross-project type checking at build time. How does this compare to npm packages shipping .d.ts files? What are the trade-offs between these two type-sharing strategies?

Any part of this still unclear? The negotiation algorithm in the Share Scope is the hardest piece — it's worth tracing through a few examples until the decision tree feels intuitive.
