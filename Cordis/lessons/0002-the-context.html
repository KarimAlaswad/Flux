Part 1: What is a JavaScript Object?

An object is a collection of key-value pairs (also called properties):

const dog = {
  name: "Rex",     // key: "name",   value: "Rex"
  breed: "Lab",    // key: "breed",  value: "Lab"
  age: 5           // key: "age",    value: 5
}
+-------------------+ | dog | | | | name -> "Rex" | | breed -> "Lab" | | age -> 5 | +-------------------+

You access a property by name:

dog.name    // "Rex"
dog.age     // 5

This is called a property read. JavaScript looks up the key and returns the value.

Part 2: What is a Proxy?

A Proxy wraps an object and intercepts operations on it. You define a handler that runs instead of the normal behavior.

Here is a plain object:

const person = { name: "Alice" }
person.name   // "Alice" -- normal property read

Now the same object wrapped in a Proxy:

const handler = {
  get(target, prop) {
    console.log("Someone is reading:", prop)
    return target[prop]
  }
}

const person = new Proxy({ name: "Alice" }, handler)
person.name   // prints: "Someone is reading: name"
              // returns: "Alice"

What happened?

WITHOUT Proxy: WITH Proxy: person.name person.name | | v v +-----------------+ +--------------------+ | Look up "name" | | HANDLER fires: | | in the object | | get(target, "name")| +-----------------+ +--------------------+ | | v v Returns "Alice" Logs "Someone is reading: name" Then looks up "name" in the object Returns "Alice"

The Proxy intercepted the property read. The handler ran code before the actual lookup happened.

Key idea: you can run custom code every time someone reads a property.

Part 3: Why Does Cordis Use a Proxy?

In Cordis, every ctx object is wrapped in a Proxy. When you write:

ctx.tools

You think you are doing a normal property read. But the Proxy intercepts it and does something extra:

You write: ctx.tools What actually happens: 1. Proxy handler fires: "Someone wants ctx.tools" 2. Handler looks up "tools" in the service store 3. Handler RECORDS: "this plugin now depends on 'tools'" 4. Handler returns the service (or undefined if not ready yet)

Why track dependencies? Because of the inject system. When you declare:

export const inject = ['tools']

You are saying: "Do not load my plugin until ctx.tools exists." The Proxy makes this possible by watching every property read.

Key insight Without the Proxy, reading ctx.tools would be invisible to the framework. The framework could not track which services your plugin needs, and could not hold your plugin PENDING until they are available.

Part 4: What is ctx?

ctx (short for "context") is the single object every Cordis plugin receives. It is the workbench where you do everything:

+---------------------------------------------------+ | ctx | | | | WHERE YOU ACT: WHAT YOU NEED: | | (register things) (declare dependencies) | | | | ctx.on(...) inject: ['tools'] | | ctx.effect(...) inject: ['llm'] | | ctx.tools.register(...) | | | +---------------------------------------------------+

Both directions go through the same object. The Proxy handles both automatically.

Part 5: What is a Service?

A Service is a named capability that lives on ctx. Think of it as a tool or feature that other plugins can use.

Some services you might find on ctx:

Service nameWhat it provides
ctx.toolsA registry where plugins can register model-callable tools
ctx.llmAccess to language model APIs
ctx.loggerLogging (console output with levels like INFO, WARN, ERROR)
ctx.eventsAn event bus for plugin-to-plugin communication

A service is registered by calling ctx.provide('name', implementation). Once registered, any plugin can access it via ctx.name.

After: ctx.provide('tools', myToolRegistry) +---------------------------------------------------+ | ctx | | | | Service Store: | | +-----------+ | | | "tools" | -> myToolRegistry (the instance) | | +-----------+ | | | +---------------------------------------------------+ Any plugin can now do: ctx.tools -> myToolRegistry

Part 6: What is ctx.tools?

ctx.tools is a Service that provides a tool registry. It is not just a list of tools — it is an object with methods for managing tools.

In the DeepSeek Harness (which uses Cordis), ctx.tools has these methods:

MethodWhat it does
ctx.tools.register(tool)Add a tool to the registry
ctx.tools.get(name)Look up a tool by name
ctx.tools.execute(exec)Run a tool (goes through the full pipeline: pre-check, execute, post-check)
ctx.tools.guard(fn)Add a permission guard (can deny tool calls)
ctx.tools.restrict(filter)Hide certain tools from the model in this scope

Part 7: What Does "Registering a Tool" Mean?

A tool is something an AI model can call. For example, a tool called read_file lets the model read files from disk. A tool called bash lets the model run shell commands.

When you register a tool, you are telling the system: "Here is a new capability the model can use." You provide:

ctx.tools.register(defineTool({
  name: 'greet',                          // what the model calls it
  description: 'Greet someone by name.',  // what the model sees
  parameters: {                           // what arguments it accepts
    name: { type: 'string', required: true }
  },
  output: {
    schema: { type: 'string' },
    render: (args, value) => [{ type: 'text', text: value }],
  },
  async execute(args) {
    return `Hello, ${args.name}!`         // the actual logic
  },
}))

Here is what happens when you register:

Step 1: You call ctx.tools.register(tool) Step 2: The tool registry stores the tool definition Step 3: The tool's schema is added to the system prompt (so the model knows the tool exists) Step 4: When the model calls the tool: a. Pre-checks run (permissions, validation) b. execute() runs c. Post-checks run (result validation) d. The result goes back to the model Step 5: When your plugin unloads, the tool is AUTOMATICALLY unregistered (no leak!)

Why "automatically"? Because registration is an effect — it tracks a disposer. When the plugin unloads, the disposer runs and removes the tool. This is the temporal composability from Lesson 1 in action.

Part 8: How inject Tracking Works

When you declare inject: ['tools'], you are creating a contract with the framework:

YOUR PLUGIN: FRAMEWORK: inject: ['tools'] "OK, I will watch for 'tools'" "I will NOT load this plugin yet" "I will hold it in PENDING state" ... "Aha! ctx.tools just appeared!" "Now I will load this plugin" ... apply(ctx) { "Dependencies are met. Running apply()." ctx.tools.register(...) "The plugin is now ACTIVE." }

The Proxy is what makes this possible. Every time your plugin reads ctx.tools, the Proxy fires and the framework notes the dependency.

The full sequence:

  1. Plugin registered — framework sees inject: ['tools']
  2. Framework checks: does ctx.tools exist? No. → Plugin stays PENDING
  3. Another plugin provides tools: ctx.provide('tools', registry)
  4. Framework notifies all waiting fibers: "tools just appeared"
  5. Your plugin re-checks: does ctx.tools exist? Yes! → Plugin moves to LOADING
  6. apply(ctx) runs — plugin is now ACTIVE

If ctx.tools disappears later (the provider unloads), your plugin automatically unloads too. When ctx.tools reappears, your plugin automatically reloads.

Spatial composability in action This is the "reactive coeffects" from Lesson 1. Plugins declare what they need. The runtime manages the dependency graph. No boot scripts. No manual ordering.

Part 9: ctx.tools vs ctx.get('tools')

These two look similar but do different things:

ExpressionWhat it doesTracks dependency?
ctx.toolsResolves via the ProxyYes — tells the framework "I need this"
ctx.get('tools')Reads without the ProxyNo — just peeking, not committing

When to use which?

  • ctx.tools — when your plugin genuinely needs this service to function
  • ctx.get('tools') — when you want to check if something exists without declaring a dependency (e.g., optional feature)
ctx.tools -> "I NEED tools. Hold me until they exist." ctx.get('tools') -> "Just curious. Do tools exist? No? OK, I'll handle it."

Part 10: Scoping with extend() and isolate()

ctx is not a flat object. It is a tree. You create child contexts for scoping:

extend() — add metadata

const child = ctx.extend({ debug: true })

This creates a child context that inherits all of ctx's services but adds its own debug property:

ctx (parent): tools -> toolRegistry logger -> loggerInstance debug -> (not set) child (created via ctx.extend({ debug: true })): tools -> toolRegistry (inherited from parent) logger -> loggerInstance (inherited from parent) debug -> true (own property, shadows nothing)

The child inherits services from the parent through the prototype chain. If you set debug on the child, the parent is NOT affected.

isolate() — separate a service scope

const isolated = ctx.isolate('tools')

This creates a child where tools resolves independently:

ctx (parent): tools -> toolRegistryA isolated (created via ctx.isolate('tools')): tools -> (empty! different scope) logger -> loggerInstance (still inherited) Now: isolated.provide('tools', toolRegistryB) ctx.tools -> toolRegistryA (parent unchanged) isolated.tools -> toolRegistryB (child has its own)

Why would you want this?

  • Running two chat sessions with different tool sets
  • Testing — give a plugin a mock without affecting the real one
  • Nested applications with different configurations

Check Your Understanding

What does a JavaScript Proxy do?
  • It makes objects faster
  • It intercepts operations (like property reads) and runs custom code
  • It creates a copy of an object
  • It deletes properties from an object
Why does Cordis wrap ctx in a Proxy?
  • For better performance
  • To track which services each plugin depends on
  • To prevent plugins from accessing services
  • To make the code look cleaner
What happens when you call ctx.tools.register(tool)?
  • The tool is sent to the AI model immediately
  • The tool is stored in the registry and added to the system prompt
  • The tool replaces an existing tool
  • Nothing, it is just a placeholder
What is the difference between ctx.tools and ctx.get('tools')?
  • They are exactly the same
  • ctx.get('tools') is faster
  • ctx.tools tracks a dependency; ctx.get('tools') does not
  • ctx.tools returns the raw object; ctx.get returns a copy
