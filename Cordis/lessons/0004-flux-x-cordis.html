Lesson 004: Flux × Cordis — From Boot to Everything On Top

Cordis Learning Workspace · Lesson 4 of ? · Mission

You learned the 7 Cordis components in Lesson 3. Now we transplant them into Flux and walk the entire stack: what happens at second zero when you double-click the app icon, all the way up to a YouTube video playing on your screen.

The One-Sentence Idea

Cordis runs everything inside one JavaScript process. Flux cannot do that — its plugins are separate OS processes in any language. So the transplant works like this:

CORDIS (in-process) FLUX (multi-process) ===================== ============================= Context + Proxy becomes The Rust skeleton's router Fiber (plugin life) becomes One supervisor per subprocess epoch string becomes Hash of provider fiber UIDs, computed by the skeleton effect / disposer becomes Shutdown handshake over IPC, then SIGTERM, then SIGKILL Service class becomes Capability declared in manifest, registered at init handshake Events (5 modes) becomes Router-implemented modes across process boundaries Proxy magic tracking becomes The explicit "inject" array in the manifest

The last row is the most important insight in this lesson: you don't need JavaScript's Proxy. Proxy was Cordis's DX sugar for auto-detecting dependencies. In Flux, the manifest's inject declaration does the same job explicitly — and it works in every language, because it is just data.

Ground Truth: What Flux Has Today

Your repo already contains the seeds of this exact architecture:

plugins/ _shared/stdin.ts <- the stdio JSON line reader (seed of the fiber handshake loop) core-manifest/ <- CORE plugin: serves manifests core-serve/ <- CORE plugin: local server core-static/ <- CORE plugin: static assets feed/ <- FEATURE plugin: unified feed flux-player/ <- FEATURE plugin: the video player player-modal/ <- UI plugin: player shell peertube/ <- PROVIDER plugin youtube/ <- PROVIDER plugin plugin.json <- { name, version, description, author } plugins/ yt-auth/ <- SUB-plugin of youtube! yt-feed/ <- SUB-plugin of youtube! yt-search <- SUB-plugin of youtube!

Notice two things. First, your plugins/youtube/plugins/yt-auth structure means recursive modularity already exists in your codebase today. Second, your plugin.json has no inject, no provides, no mediaTypes yet — that is exactly what this lesson adds.

The Layer Map

Here is the full stack, from the metal to the pixels. Each layer only knows the layer below it. This is your rule 15a made physical: messages always travel down through the skeleton, never sideways.

One build works on every provider. | v LAYER 3 PROVIDER PLUGINS (the media sources) youtube, peertube, spotify, reddit... each is one Fiber = one subprocess. provides capabilities: "youtube", "shorts.source" | | (JSON-RPC over stdin/stdout) v LAYER 2 KERNEL CONTEXT (root fiber uid=0) Core services load as ordinary plugins: http, storage, manifest-registry, event-router. Layer 1: The Rust Skeleton (the Dumb Host)

Your rule: "The host stays dumb. It routes by method prefix and does nothing else." Here is its complete job description — if a feature is not on this list, it does not belong in the skeleton:

Owned by skeletonWhat it means
WindowOpen the webview, load the React shell
SpawnFork plugin subprocesses, wire stdin/stdout pipes
RouteMethod prefix to fiber lookup, forward bytes both ways
BridgeTranslate between protocol versions (JSON-RPC v1, msgpack...)
CleanupGraceful shutdown handshake, then kill orphans

Compare with Cordis: the skeleton is what remains when you delete everything smart from Context. In Cordis, the Proxy handler is smart (it walks fibers, computes epochs). In Flux, that intelligence moves up into Layer 2's services, and the skeleton keeps only mechanical routing.

WHY THIS MATTERS (your rule 14): Adding 100+ plugins requires ZERO changes to routing code. The router table is DATA built at runtime from manifests. A new plugin = one more row in a HashMap. That's it.

Layer 2: The Kernel Context

The first thing the skeleton does after opening the window is create the root context. In Cordis this was new Context(). In Flux it is the same idea with one twist: core services are ordinary plugins too.

new KernelContext() (root fiber, uid=0, ACTIVE) ctx.plugin(core-manifest) PENDING -> LOADING -> ACTIVE provides "manifests" (scan plugins/, parse plugin.json) ctx.plugin(core-serve) inject: ["manifests"] waits until "manifests" exists provides "serve" (localhost HTTP for streams) ctx.plugin(core-static) inject: ["serve", "manifests"] provides "ui.assets" (plugin frontend bundles) Each arrow is an EPOCH transition: PENDING (deps missing) -> LOADING (deps appeared) -> ACTIVE

This is your rule 2 in action ("the core needs to be as small as possible"): there is no privileged core code. Delete core-serve and write core-serve-rs in Rust — as long as it provides the same capability name, nothing above notices.

Layer 3: Provider Plugins (Fibers Over Processes)

Here is where Cordis's Fiber meets your subprocess model. Each plugin gets one Fiber owned by the skeleton. The fiber's state machine drives the real OS process:

THE HANDSHAKE (what _shared/stdin.ts will grow into) skeleton youtube subprocess (any language) -------- --------------------------------- fiber: PENDING deps missing? none. epoch ready -> LOADING spawn("bun run youtube/main.ts") pipe stdin/stdout starts, waits on stdin send line 1: {"id":1,"method":"init", "params":{ "config": {...user settings}, "inject":["http","storage"], "grants":["net","fs.cache"]}} reads init via stdin.ts constructs its services send line 2 (response): {"id":1,"result":{ "provides":["youtube"], "emits":["feed.updated"], "components":[ "shorts.card","video.card"]}} declares capabilities back skeleton registers provides -> reflect-store updated -> dependents' epochs recompute fiber: ACTIVE

Three details worth pausing on:

  1. The manifest is the promise; the handshake is the proof. plugin.json says what the plugin intends to provide. The init response confirms what it actually provided. The skeleton trusts the response, not the promise — this is how a plugin written in Python can evolve without touching its manifest.
  2. inject travels as data. The skeleton resolves "http" and "storage" to capability handles (small tokens the plugin can spend on routed calls). The plugin never sees process IDs or file descriptors.
  3. Language disappears at this boundary. The skeleton cannot tell whether youtube is Bun, Go, or Rust. That is rule 12 working exactly as designed.

Layer 4: Feature Plugins Attach to Media Types

Cordis events had 5 dispatch modes. Flux keeps all five, but now they cross process boundaries — the router implements the semantics by waiting (or not waiting) for responses:

ModeSkeleton implementation
emitFire-and-forget broadcast to subscriber pipes
waterfallSequential RPC chain; each subscriber may transform params; skip = pass through unchanged
parallelConcurrent fan-out, join when all respond or timeout
bailFan-out in order, stop at first non-null result, return it
serialIn-order RPC, stop at first error/bail signal

Features attach to media types, never to providers. The declaration lives in the manifest:

auto-scroll/plugin.json { "name": "auto-scroll", "inject": ["media.events"], "hooks": { "shorts.playback.started": "onPlay" } } youtube declares it emits shorts.playback.started (via media.events) peertube declares the same => auto-scroll works on BOTH with zero provider awareness. Community builds once, works everywhere. (App rule 3)

Layer 5: UI Composition

The React shell is also a plugin consumer. It renders slots, and fills each slot by querying the component registry that Layer 3's handshake populated:

THE SHELL'S ONLY QUESTION: "registry.components('shorts.card') -> ordered list" [ youtube:ShortsCard, <- declared by youtube handshake peertube:ShortsCard ] <- declared by peertube handshake User picks a default per slot (opinionation slider, rule 7): slot 'video.player' -> flux-player (chosen) player-modal (alternative) Meta-plugins can preset all slots in one click, user can still override any single slot.

Boot Sequence Timeline

All layers together, second zero to ready:

t=0 OS starts flux binary t=1 L1 skeleton opens window, loads React shell t=2 L2 root context created (root fiber ACTIVE) t=3 core-manifest loads, scans plugins/, parses manifests t=4 core-serve PENDING (waiting for "manifests") core-static PENDING (waiting for "serve") t=5 "manifests" provided -> serve epoch fires -> LOADING t=6 serve ACTIVE -> static epoch fires -> LOADING -> ACTIVE t=7 providers spawn: youtube fiber LOADING, peertube LOADING (handshakes run concurrently - processes are parallel) t=8 youtube provides "youtube" + components feed plugin epoch fires: inject ["feed.sources"] met t=9 feed ACTIVE; shell queries slots; cards render t=10 READY - user sees composed home screen (late plugins keep loading silently in background)

Notice there is no boot order file anywhere. Order emerges from epochs — exactly like Cordis, but the ticks are process handshakes instead of function calls.

Life of One Action: You Tap Play on a Short

The full journey of a single click, top to bottom and back:

1 React card (youtube's ShortsCard) fires: call "media.resolve" { source:"youtube", id:"abc123" } | 2 L1 router: prefix "media.*" -> owner = media-core fiber | 3 media-core (a plugin!) sees source=plugin:youtube -> call "youtube.resolve" routed to youtube subprocess | 4 youtube resolves stream URL + metadata -> result flows back up the same chain | 5 media-core returns { streamUrl, mediaType:"shorts" } | 6 shell renders slot 'video.player' -> flux-player mounts | 7 flux-player calls "media.playback.started" EVENT waterfall across ALL subscribers of shorts: sponsorblock: trims segments (transforms params) subtitle-fetcher: adds track (transforms params) auto-scroll: queues next short (observes only) watch-history: records (observes only) | 8 Video plays. Every participant was a separate process in a possibly different language. Nobody knew anybody.

Step 7 is rule 15a made real: the skeleton owns the wire, so it can run a waterfall across processes exactly like Cordis ran one across functions.

Dynamic Lifecycle: Install, Remove, Update

This is where epochs earn their keep. Watch the cascade when you disable YouTube at runtime:

USER DISABLES YOUTUBE youtube fiber: ACTIVE -> UNLOADING graceful handshake: send {"method":"dispose"} wait flush window (say 3s) for plugin to clean up then SIGTERM, then SIGKILL (escalation ladder) disposers recorded at init run here: cache purge, token revoke, temp file delete fiber: DISPOSED skeleton removes provides ["youtube", components...] | every dependent recomputes its epoch -> INACTIVE | feed fiber: ACTIVE -> UNLOADING -> PENDING (not killed forever - DORMANT, waiting) | shell re-queries slots -> youtube cards vanish cleanly LATER: USER INSTALLS "youtube-v2" (provides same caps) new fiber uid=41 -> LOADING -> ACTIVE | dependents' epochs change INACTIVE -> ":41:..." | feed reloads AUTOMATICALLY. No restart. No code changes. Cordis's promise, kept across process boundaries.

The Bridge: Protocol Evolution

Your rule 15: plugins must work forever, even when the wire format changes. Because only the skeleton touches the wire, the bridge is one translation table:

OLD PLUGIN (jsonrpc 1.0) NEW PLUGIN (msgpack) | | [ SKELETON CODEC BRIDGE ] - normalizes both to the | one internal object model { id, method, result, error } (skeleton fields only) | payloads pass through OPAQUE - never inspected, never validated, never interpreted (rule 15b)

Manifests declare "protocol": "msgpack"; omitted means JSON. Adding a format = adding an adapter row in the bridge, never migrating a plugin.

Recursion: Sub-Plugins Are Nested Contexts

Your session-2 insight (recursive modularity) is already visible in your repo: youtube/plugins/yt-auth. Here is how it scales forever:

ROOT CONTEXT (skeleton) +-- fiber: youtube (subprocess) +-- ITS OWN mini-context inside that process +-- sub-fiber: yt-auth provides "yt.session" +-- sub-fiber: yt-search inject ["yt.session"] +-- sub-fiber: yt-feed inject ["yt.session"] +-- fiber: peertube (subprocess) +-- its own children... Same rules at every depth: - declare, don't call by name - epochs gate lifecycles - parent owns child's cleanup

A big plugin never becomes an unmaintainable monolith — it becomes a context with small children, each replaceable in any language.

What We Deliberately Do NOT Copy

Being honest about what to leave behind is as important as what to transplant:

  • Proxy auto-tracking. Beautiful in JS, impossible across languages. The manifest's inject array is the explicit, portable equivalent. Trade-off: you must declare dependencies instead of having them discovered. Gain: every language gets identical treatment.
  • In-process event performance. Cordis fires millions of events per second in-memory. Flux pays a pipe round-trip per event. Fine for UI-scale events; never ship video frames through the router — streams go peer-to-process or direct URLs, control goes through the skeleton.
  • Synchronous service access. ctx.tools returns instantly in Cordis. Across a process it cannot. Flux capability calls are async RPC, so plugin code looks like normal async code in whatever language it uses.

Honest Open Questions

  1. Restart cost. A Cordis fiber reloads in microseconds; a Flux subprocess reload costs process spawn + handshake (tens of ms). Mitigation later: suspend/resume instead of kill, or keep runtimes warm.
  2. Who computes epochs? The skeleton (Rust) must. That means the reflect-store and epoch logic are real Rust code — small (~200 lines), but they ARE the smartest part of the host. Watch this boundary: if it grows logic, promote that logic into a Layer-2 plugin.
  3. Security model. Grants at handshake are the seed; sandboxing subprocesses (seccomp/landlock on Linux) is future work.
  4. Waterfall latency. A 5-subscriber waterfall over pipes is 5 sequential round-trips. Acceptable for control events; measure before using waterfalls in hot paths.

Quiz

Quiz 4.1

A new provider "vimeo" appears while feed is ACTIVE with inject: ["feed.sources"]. What happens?

Answer: b - Wait: vimeo provides a NEW source, so feed.sources epoch changes from ":7" to ":7:41". Epoch changed = unload then reload. Feed restarts once and now aggregates both providers.

Quiz 4.2

Why does Flux not need JavaScript's Proxy for dependency tracking?

Answer: b - Proxy was Cordis's DX sugar inside one JS runtime. Cross-language, the portable equivalent is declarative data: the inject array. Same epoch machinery, zero magic.

Quiz 4.3

The skeleton's codec bridge receives a msgpack message from a new plugin addressed to an old JSON-RPC plugin. What does it do with the payload?

Answer: b - Rule 15b: payloads are opaque. The bridge translates shape between declared protocols; meaning belongs to the plugins.
