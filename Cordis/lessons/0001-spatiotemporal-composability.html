Lesson 001: What is Spatiotemporal Composability?

Cordis Learning Workspace · Lesson 1 of ? · Mission

The Problem

You have a system made of plugins. At runtime, you need to:

  1. Load a plugin — it starts doing things (opening connections, registering handlers, starting timers)
  2. Unload a plugin — it stops doing things
  3. Reload a plugin — maybe the code changed, maybe the config changed

This sounds simple. It is not. Two things go wrong.

Dimension 1: Time (Temporal Composability)

When a plugin loads, it creates side effects — things that persist after the plugin's apply() function returns:

  • An event listener on ctx.on('message', handler)
  • A timer via setInterval()
  • An open database connection
  • A registered tool or command

When the plugin unloads, all of these must be undone. Not most of them. All of them.

The Problem Most plugin systems can remove a plugin's code. They cannot guarantee its side effects are fully removed. After repeated load/unload cycles, you accumulate leaked listeners, orphaned timers, and stale connections. The system slowly degrades.

Temporal composability asks: when a component is removed, can all of its side effects be completely reverted?

The word "temporal" refers to time — the effects happen over time (load, run, unload), and we need to undo them in time.

What Flux does today

In your Flux system, plugins are spawned as subprocesses. When you kill a process, the OS reclaims its memory and file handles. But what about:

  • Event listeners the plugin registered on the host's event bus?
  • Hooks the plugin declared in the registry?
  • State the plugin wrote to shared memory?

Flux doesn't track these. When a plugin dies, its traces remain until the host restarts.

Dimension 2: Space (Spatial Composability)

Plugins depend on each other. A "greet" plugin needs the "tools" registry to exist before it can register itself. A "logger" plugin needs the "database" to be available before it can write logs.

Spatial composability asks: can components declare what they depend on, and have the runtime reactively manage those dependencies?

The word "spatial" refers to relationships — where plugins sit relative to each other in the dependency graph.

The Problem Most plugin systems use manual boot ordering — you list plugins in the right order in a config file, and if you get it wrong, things crash or silently fail. When a dependency disappears at runtime (a provider crashes, a config changes), dependent plugins either crash too or keep running with stale references.

What Flux does today

In Flux, plugin load order is determined by the order they appear in the config. The resolve_hook command checks if a hook exists at call time — but if it doesn't exist, the caller gets an error. There's no "wait until it exists" mechanism.

If a plugin that provides hooks dies, every plugin that depends on those hooks breaks silently.

The Two Dimensions Together

These dimensions are orthogonal — they're independent problems that can be solved separately. But Cordis solves both simultaneously with two primitives:

Dimension Question Cordis Solution
Temporal Can we undo all side effects? Revertible effects — every ctx.effect() registers a disposer (undo function). Unloading runs disposers in reverse order.
Spatial Can we declare and manage dependencies? Reactive coeffects — inject: ['tools'] holds the plugin PENDING until ctx.tools exists. If it disappears, the plugin unloads. When it returns, the plugin reloads.

Why "Spatiotemporal"?

The paper's insight is that these two dimensions unify into a single concept. The same ctx object is:

  • Where you act — you call ctx.effect() to register side effects (temporal)
  • What you declare — you set inject to say what you need (spatial)

This unification is what makes "install," "dependency changed," and "remove" the same underlying operation. The runtime handles all three cases with the same machinery.

+-----------------------------------------------+ | Context (ctx) | | | | +--------------------+ +------------------+ | | | Where you act | | What you declare | | | | (effects) | | (coeffects) | | | | | | | | | | ctx.effect(...) | | inject: ['tools']| | | | ctx.on(...) | | inject: ['llm'] | | | | ctx.provide(...) | | | | | +--------------------+ +------------------+ | | | | Both directions go through the same object. | | The runtime manages both automatically. | +-----------------------------------------------+

A Concrete Example

Here's a Cordis plugin that declares a dependency and registers a side effect:

export const name = 'reminders'
export const inject = ['database', 'logger']  // coeffect: I need these

export function apply(ctx: Context) {
  // effect: a timer that checks for due reminders
  const timer = setInterval(() => {
    ctx.logger.info('checking reminders...')
  }, 60_000)

  // revertible effect -- this runs when the plugin unloads
  ctx.effect(() => () => clearInterval(timer))

  // event listener -- also tracked as an effect
  ctx.on('message', async (session) => {
    const due = await ctx.database.get('reminders', {
      channelId: session.channelId
    })
    if (due.length) {
      await session.send(`You have ${due.length} reminder(s).`)
    }
  })
}

What happens when this plugin unloads:

  1. The event listener on 'message' is removed
  2. The clearInterval disposer runs — the timer stops
  3. The plugin's fiber transitions to DISPOSED

No leaks. No stale references. The system is exactly as if the plugin never existed.

The Guarantee

Cordis proves (mathematically) that spatiotemporal composability carries from a single component to a whole system. This means:

  • If every plugin individually cleans up properly, the whole system cleans up properly
  • Loading plugin A, then B, then unloading A, then reloading A — converges to the same state as loading A and B directly
  • Hot-reloading a plugin is safe: the old instance is fully unwound before the new one starts

This property is called confluence — however you reached a configuration, the final state is the same.

Check Your Understanding

A plugin registers a timer and an event listener. When the plugin is unloaded, what order are they cleaned up?
  • In the order they were registered
  • In reverse order (most recent first)
  • In random order
  • The runtime doesn't track this
What happens to a plugin that declares inject: ['tools'] when ctx.tools disappears?
  • It crashes with an error
  • It keeps running with a stale reference
  • It automatically unloads (all effects are reversed)
  • Nothing happens until the next call
What is "confluence" in the context of Cordis?
  • Plugins run in parallel
  • Dependencies form a directed acyclic graph
  • The final state depends only on which plugins are enabled, not the order they were loaded/unloaded
  • The runtime merges conflicting configurations
