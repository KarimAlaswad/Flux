The Big Picture

Cordis has 7 components. Each lives in its own source file. Here is every component and its role:

+------------------------------------------------------------------+ | CORDIS SYSTEM | | | | +------------------+ +------------------+ +----------------+ | | | Reflect | | Events | | Registry | | | | | | | | | | | | Service store | | Event bus | | Plugin loader | | | | Proxy handler | | 5 dispatch modes | | Fiber creator | | | | Dependency track | | Hook management | | Config valid. | | | +--------+---------+ +--------+---------+ +-------+--------+ | | | | | | | +----------------------+----------------------+ | | | | | +---------+---------+ | | | Context | | | | (the hub) | | | +----+--------+------+ | | | | | | +--------+--+ +---+--------+ | | | Fiber | | Service | | | | | | (base) | | | | Lifecycle | | | | | | Effects | | Capability | | | | Epochs | | base class | | | +-----------+ +-------------+ | | | | +--------------------------------------------------------------+ | | | utils | | | | symbols, DisposableList, createCallable, getTraceable | | | +--------------------------------------------------------------+ | +------------------------------------------------------------------+

Now let me explain each one, then show how they connect.

Component 1: Reflect (the Proxy Engine)

The ReflectService is the most critical component. It does two things:

A. The Proxy Handler

When you write ctx.tools, the Proxy fires. Here is exactly what happens, step by step:

You write: ctx.tools Step 1: Proxy get handler fires Is "tools" a special property? (symbol, _, number) No -> continue Step 2: Is "tools" on the Context object directly? (Did someone call ctx.provide('tools', x)?) Yes -> return it via getTraceable() No -> continue Step 3: Is "tools" an accessor? (defined via ctx.accessor()) Yes -> call the accessor's get() function No -> continue Step 4: Walk up the fiber tree: Current fiber -> parent fiber -> grandparent -> ... -> root For each fiber: Is "tools" in fiber.store? (was it provided here?) Yes -> return the service Is "tools" in fiber.inject? (was it required here?) Yes -> but not found! -> throw error Is the isolation key the same as parent's? No -> isolation boundary -> stop walking Continue to parent fiber Root reached, not found -> throw error

B. The Service Store

Reflect maintains two internal maps:

reflect.store: { isolationSymbol -> { name, value, fiber, check } } Maps each service name's isolation symbol to its implementation reflect.props: { serviceName -> { type: 'service' } } Maps service names to their type (service or accessor)

When you call ctx.provide('tools', registry), Reflect:

  1. Creates an isolation symbol if none exists
  2. Creates an Impl object: { name: 'tools', value: registry, fiber: currentFiber }
  3. Stores it in reflect.store[key]
  4. Notifies all fibers that depend on 'tools'

C. Mixins (delegating ctx.on, ctx.emit, etc.)

When you call ctx.on('event', handler), you are actually calling ctx.events.on('event', handler). This works because Reflect sets up accessor properties that delegate to the real services:

ctx.on -> forwards to ctx.events.on ctx.emit -> forwards to ctx.events.emit ctx.plugin -> forwards to ctx.registry.plugin ctx.effect -> forwards to ctx.fiber.effect ctx.provide -> forwards to ctx.reflect.provide ctx.get -> forwards to ctx.reflect.get ctx.set -> forwards to ctx.reflect.set

This is why ctx feels like it has all these methods. They are all delegated through accessors defined in the ReflectService constructor.

Component 2: Fiber (the Lifecycle Engine)

A Fiber is one loaded plugin instance. Every time you call ctx.plugin(spec), a new Fiber is created. It manages the plugin's entire life.

The State Machine

PENDING -----> LOADING -----> ACTIVE | | | | | v | | FAILED (if apply() throws) | | | | | v | +<----------- UNLOADING | | | v +<------------------------ DISPOSED PENDING: Dependencies not met yet. Plugin is dormant. LOADING: Dependencies met. apply() is executing. ACTIVE: Plugin is running. Effects are live. FAILED: apply() threw an error. Plugin is dead. UNLOADING: Disposing all effects (in reverse order). DISPOSED: Fully cleaned up. uid is null.

The Epoch System (how PENDING becomes ACTIVE)

Each fiber has an epoch string — a fingerprint of its dependencies. When you declare inject: ['tools', 'llm'], the epoch is built from the unique IDs of the fibers that provide those services:

Plugin A: inject = ['tools', 'llm'] When 'tools' appears (uid=3) and 'llm' appears (uid=7): epoch = ":3:7" (concatenated UIDs) When 'tools' disappears: epoch = INACTIVE (missing dependency) When 'tools' reappears (uid=12, different provider): epoch = ":12:7" (new UID, new epoch -> triggers reload)

When the epoch changes:

  • INACTIVE → real value → _reload() (plugin starts)
  • real value → INACTIVE → _unload() (plugin stops)
  • real value A → real value B → unload then reload (plugin restarts)

The Effect System

When you call ctx.effect(() => { ... return () => cleanup() }), the Fiber:

  1. Runs the callback immediately
  2. Captures the returned disposer (the cleanup function)
  3. Stores the disposer in fiber._disposables
  4. When the fiber unloads, runs all disposers in reverse order
Plugin registers 3 effects: effect 1: timer (disposer: clearInterval) effect 2: event listener (disposer: removeListener) effect 3: database connection (disposer: close) When plugin unloads: Disposer 3 runs (database.close) Disposer 2 runs (removeListener) Disposer 1 runs (clearInterval) All cleaned up. No leaks.

Component 3: Events (the Communication Bus)

Plugins talk to each other through events. The EventsService manages the event bus with 5 dispatch modes:

ModeWhat it doesAnalogy
emitFire all listeners, no return valueAnnouncement on a loudspeaker
waterfallChain listeners, each transforms the result. Can short-circuitAssembly line where each worker modifies the product
parallelFire all listeners concurrently, wait for allMultiple workers doing the same task in parallel
serialFire listeners one by one, stop at first bailQueue where one person can stop the line
bailFire listeners, stop at first non-null returnFirst-come-first-served, winner takes all

How events connect to the effect system

When you call ctx.on('message', handler), the hook is registered as an effect. This means:

  • The hook is tracked by the current fiber
  • When the fiber unloads, the hook is automatically removed
  • You never need to manually call removeListener

Component 4: Registry (the Plugin Manager)

The RegistryService manages plugin registration. It maps plugin callbacks to their Runtime objects:

registry._internal: Map of Function to Runtime Runtime = { name: "my-plugin", callback: applyFunction, fibers: DisposableList of Fiber, Config: schema (optional config validation) } When you call ctx.plugin(myPlugin): 1. Resolve myPlugin to its callback function 2. Get or create a Runtime for that callback 3. Create a new Fiber for this instance 4. Push the Fiber into runtime.fibers 5. Return a PromiseLike that resolves when fiber is active

Key insight: calling ctx.plugin(samePlugin) twice creates two Fibers for the same Runtime. When all fibers are disposed, the Runtime is cleaned up.

Component 5: Service (the Capability Base Class)

The Service class is a base for long-lived services. When you extend it:

export class ToolRuntime extends Service {
  constructor(ctx: Context) {
    super(ctx, 'tools')  // registers as ctx.tools
  }
}

The constructor calls ctx.reflect.provide('tools', self), which registers the service instance. After that, any plugin with inject: ['tools'] can access ctx.tools.

Component 6: Context (the Hub)

The Context is the composition root that wires everything together. When new Context() is called:

new Context() | +-> 1. Create empty isolate map +-> 2. Create empty intercept map +-> 3. Wrap self in Proxy (ReflectService.handler) +-> 4. Set root = proxied self +-> 5. Create root Fiber (uid=0, ACTIVE immediately) +-> 6. Create ReflectService (registers as ctx.reflect) +-> 7. Create EventsService (registers as ctx.events) +-> 8. Create RegistryService (registers as ctx.registry) +-> 9. All services are now available +-> 10. Ready for ctx.plugin() calls

The root fiber is special: it has no parent, it is created ACTIVE immediately, and it is never disposed until the entire context is destroyed.

Component 7: utils (the Glue)

The utils module provides shared helpers used by all other components:

HelperPurpose
DisposableListArray of disposers with bulk dispose
createCallableMakes an object callable (e.g., ctx.logger())
getTraceableWraps service in a tracked Proxy for dependency detection
joinTraceBuilds epoch strings from dependency UIDs

The Complete Data Flow

Now let me show how everything connects in a real scenario. Here is what happens when an app starts:

STEP 1: App creates context new Context() STEP 2: App loads the Tools plugin ctx.plugin(toolRegistryPlugin) Registry creates a Fiber for this plugin Fiber state: PENDING -> LOADING apply() runs, ctx.tools = new ToolRegistry(ctx) ToolRegistry constructor calls ctx.reflect.provide('tools', self) Registry stores: reflect.store["tools"] = { value, fiber } Fiber state: LOADING -> ACTIVE STEP 3: App loads the AI LLM plugin ctx.plugin(aiLlmPlugin) LLM declares: inject: ["tools"] Fiber checks: is "tools" in reflect.store? Yes! -> LLM can load apply() runs, ctx.llm = new AiLlm(ctx) LLM registers events: ctx.on("chat", handler) LLM registers effects: ctx.effect(() => monitorTokens()) Fiber state: PENDING -> LOADING -> ACTIVE STEP 4: App loads a user's custom plugin ctx.plugin(myCustomPlugin) Custom plugin declares: inject: ["tools", "llm"] Fiber checks: both in reflect.store? Yes! apply() runs, accesses ctx.llm and ctx.tools Registers event listener: ctx.on("chat", myHandler) Registers effect: ctx.effect(() => myCleanup()) Fiber state: PENDING -> LOADING -> ACTIVE STEP 5: User clicks a button, triggering chat ctx.emit("chat", message) EventsService finds all "chat" listeners Calls them in order: 1. myHandler (from custom plugin) 2. handler (from LLM plugin) Each handler can use its ctx access Each handler's cleanup runs when its fiber unloads STEP 6: User removes the custom plugin Fiber.dispose() is called Fiber state: ACTIVE -> UNLOADING Runs disposers in reverse order: 1. myCleanup() runs 2. "chat" hook is removed Fiber state: UNLOADING -> DISPOSED Reflect removes "tools" and "llm" from store Notify other fibers: LLM fiber loses its dependencies LLM fiber: ACTIVE -> UNLOADING -> DISPOSED Or: LLM fiber goes to PENDING (waiting for new provider)

Flux Comparison

Now let me connect this to your Flux system:

Cordis ComponentFlux EquivalentKey Difference
Context (ctx)PluginContextCordis uses Proxy + Reflect for dynamic DI. Flux uses explicit register/get.
FiberPlugin lifecycleCordis has a formal state machine + epoch-based reload. Flux has simpler activate/deactivate.
ServiceBasePluginBoth provide capabilities. Service has built-in DI tracking via Proxy.
EventsEventBus (via IPC)Cordis has 5 dispatch modes. Flux uses JSON-RPC over process boundaries.
RegistryPlugin loadingCordis maps callbacks to Fibers. Flux loads from directories.
ReflectNo equivalentFlux does not have automatic dependency tracking via Proxy.

The biggest architectural difference: Cordis tracks dependencies automatically via Proxy. When you write ctx.tools, Cordis knows you depend on "tools" without you declaring it anywhere (except the inject array). In Flux, you call ctx.get('tools') explicitly and there is no automatic tracking.

Quiz

Quiz 3.1

What is the correct order of component creation when you call new Context()?

Answer: b - The root Fiber is created first (step 5), then Reflect (step 6), then Events (step 7), then Registry (step 8). The root Fiber must exist before services can register on it.

Quiz 3.2

When a plugin declares inject: ['tools'], what happens if "tools" is later removed from the reflect store?

Answer: b - The fiber detects the epoch change (active -> INACTIVE) and unloads. It goes to PENDING state. If a new "tools" provider appears, it will reload automatically.

Quiz 3.3

Why does Cordis need the Reflect component when it could just use a regular Map to store services?

Answer: b - A Map would give you key-value storage, but Proxy gives you three things a Map cannot: (1) automatic dependency tracking when you access properties, (2) scoped lookups that walk up the fiber tree with isolation boundaries, and (3) the ability to intercept property access for extend(), isolate(), and lifecycle hooks.
