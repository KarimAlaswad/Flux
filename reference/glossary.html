System Design Glossary

Reference document · Last updated: Lesson 3

The core vocabulary of system design — terms used consistently across all lessons in this workspace. Each term includes a concise definition and how it maps to Flux.

Modularity
Dividing a system into distinct, replaceable parts that each own a specific responsibility. → Flux's plugins (yt-feed, yt-auth, peertube) are modules, each owning one data source.
Interface (contract)
The shared boundary between two modules — what one exposes and the other consumes. A good interface hides implementation details. → The JSON-RPC protocol between Flux's Rust host and plugin subprocesses: {"id":1,"method":"action","params":{}}.
Coupling
How much one module depends on the internal details of another. Low coupling = good (modules can change independently). High coupling = bad (changing one breaks the other). → Flux's plugins are loosely coupled via subprocess + JSON-RPC; they don't share memory.
Cohesion
How closely the responsibilities within a single module belong together. High cohesion = good (everything in a module serves a unified purpose). Low cohesion = bad (a module does many unrelated things). → yt-auth handles only auth; yt-feed handles only feed fetching. That's high cohesion.
Separation of Concerns
Each module should address a distinct, separable concern. Overlapping concerns create coupling. → Flux separates auth (yt-auth) from data fetching (yt-feed) from UI (feed-widget).
Information Hiding
A module should conceal its internal workings from the outside, exposing only what other modules need. → Flux plugins don't expose their internal state; they only respond to method calls.
Abstraction Layer
A simplified interface that hides messy underlying complexity. → The callHook / resolveHook Tauri commands are abstraction layers over the plugin discovery and routing system.
Leaky Abstraction
An abstraction that forces the consumer to understand the underlying complexity anyway. → If a Flux plugin consumer needs to know about subprocess spawning to use a plugin, the plugin abstraction leaks.
Architecture
The high-level structure of a system: its modules, their relationships, and the principles governing their design and evolution over time. → Flux's architecture: Tauri shell → Rust host (timeout-routed IPC) → subprocess plugins → React/Web Component frontend.
Trade-off
A design decision where improving one quality (e.g., flexibility) comes at the cost of another (e.g., simplicity). There are no perfect designs — only trade-offs. → Flux chose subprocess plugins for isolation (good) at the cost of IPC serialization overhead (the trade-off).
Tactical Programming
Focusing on getting today's feature working without regard for the system's long-term structure. Necessary in small doses; pathological as the default mode. → Adding one more field to the JSON-RPC response without thinking about the protocol structure.
Strategic Programming
Investing extra effort now to leave the system better than you found it, paying down design debt so future changes stay cheap. → Stabilizing the plugin RPC schema before adding more plugin types.
Registry
A directory that maps capabilities to providers. Plugins register "I can do X" with the registry. Consumers ask "Who does X?" and get back an address. A registry decouples what is needed from who provides it. → Flux's resolve_hook command is a registry query — it searches the plugin list by hook name and returns the provider. Currently embedded in the Rust host; could be a separate swappable piece.
Capability
A named, addressable unit of functionality that a plugin provides or consumes. Named by convention (e.g., feed.video, video.player). The registry maps capability names to providers. → Flux's hooks are capabilities: hooks: ["feed.video", "yt-auth"] declares what the plugin provides to the system.
Discovery
The process of finding which provider offers a particular capability at runtime, rather than hardcoding it at compile time. Discovery is the opposite of hardcoding. → Calling resolveHook("feed.video") is discovery. Calling __pluginRpc("yt-feed.feed", {}) is not discovery — it hardcodes the provider name.
Service Locator
A pattern where a central object (the locator) knows how to provide dependencies on demand. A more powerful version of a registry — it can lazily create services if they aren't running yet. Often debated as an anti-pattern because it hides dependencies. → Flux's call_hook is a service locator: it resolves the hook and calls the method in one step.
Microkernel (Plugin Architecture)
An architecture with a minimal core that handles only plugin lifecycle and inter-plugin communication. Everything else — features, data sources, UI — lives in plugins. The core must be so small that rewriting it is cheap. → Flux's goal: a core that just starts the Registry and spawns plugins. The current ~317-line lib.rs is close but still too big.
Extension Point
A place in the system where plugins can hook in to add functionality. Defined by a contract (interface, message format, hook name). The core defines the extension point; plugins implement it. → Flux's hook system (hooks: ["feed.video"]) are extension points. Any plugin can implement a hook.
Process Supervisor
A program that watches over other programs and restarts them if they crash. The supervisor's one job is keeping things running. It doesn't care what the programs do. → s6 (from the research) is a supervisor: if a plugin crashes, s6 detects it (via SIGCHLD) and re-runs the ./run script. No code change, no manual restart.
Share Scope
A runtime registry of shared dependencies in Module Federation. Maps (packageName, shareKey, shareScope) to a module factory instance. Participants register their shared deps when their remoteEntry.js loads; the scope negotiates which version wins based on singleton, requiredVersion, and shareStrategy. → Host registers react@18.2.0, remote registers react@^18 — Share Scope matches them and provides one React instance to both.
Host (Consumer)
In Module Federation, the application that loads and consumes modules from remotes. Declares which remotes it depends on via the remotes config. → Flux's App.tsx would be the host if it loaded plugin widgets via MF: import('feed-widget/Card').
Remote (Producer)
In Module Federation, the application that exposes modules for consumption. Declares what it offers via the exposes config. Produces a remoteEntry.js (or mf-manifest.json) as its manifest. → A plugin like yt-video-card would be a remote, exposing "./Card": "./src/Card.tsx".
remoteEntry.js
A bootstrap manifest generated by a Module Federation producer. When loaded, it registers the producer in the Share Scope, exposes module factory functions, and declares shared dependency requirements. Not the application code — the registry metadata. → MF runtime fetches http://cdn/my-app/remoteEntry.js to discover what the remote offers and needs.
Bridge
Module Federation's cross-framework application sharing mechanism. Uses a render/destroy lifecycle contract on a DOM node — any framework (React, Vue) exports a provider with these two methods, and any host can load it, regardless of its own framework. → A React host loads a Vue remote via createRemoteAppComponent({ loader: () => import('vue-app/export-app') }) — the internal framework is invisible to the host.
Version Negotiation
The process by which Module Federation's Share Scope decides which version of a shared dependency to use when multiple participants offer different versions. Checks: is the package already registered? Is singleton: true? Do version ranges overlap? Result: reuse the loaded instance, load a separate copy, or error on incompatible singletons. → Host has react@18.2.0, remote needs react@^18 — compatible, reuse. Host has react@18, remote needs react@^19 — incompatible singletons, error.
